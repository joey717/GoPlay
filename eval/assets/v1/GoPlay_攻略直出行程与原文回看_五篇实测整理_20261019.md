# GoPlay：攻略直出行程、自然补充与原文回看

2026-10-19｜产品建议与五篇真实素材人工整理样例，待小Q评估；不是生产功能验收，不改动已冻结PRD或DEMO。

## 交给用户的应是行程，不是分析报告

用户把几篇攻略交给GoPlay，系统结合已选日期、航班、住宿、已购门票和用户约束，直接展示一份完整行程草案。多篇推荐、分歧、避雷和来源数量只用于后台判断，不要求用户先读分类清单、逐个选点，再点击生成。

景点卡上的攻略内容是自然补充：有一条好路线就留下路线，有具体心得就留下心得，有Tips就留下Tips。没有固定五类模板，没有“攻略未明确”占位，不为凑字段补编。重复内容合并，有价值的差异保留。单篇的具体玩法和餐厅体验也有价值，可以补入已选景点；不能把“单篇只能进候选”作为硬规则。

初排生成的是可浏览草案。可以用现有“采用这版”确认提交，而不用逐点确认。再次上传素材或微调时，已订、锁定和用户手改仍受现有护栏保护；自动展示结果不等于静默覆盖既有行程。

## 五篇素材读到了什么

本次读取五篇目标笔记正文，第2篇全部9张文字图，以及第1篇路线封面。第3、4、5篇其余摄影图未逐张检查，评论未进入五篇攻略的统计。本次使用已登录浏览器，不代表匿名HTTP、云服务器或产品接口已经验证成功。票价、房态、营业、天气、潮汐和地图交通均未核验。

第1篇提供五天四晚路线、早班船和日落提醒；长段卖车内容不进入旅行整理。正文和封面的Day分配有差异，因此只保留地点、区域与提示，不机械复制全部日期顺序。第2篇正文基本只有话题，信息集中在九张图：路线、预约提醒、天气、住宿区域、两岛取舍和餐厅。只读正文或只处理前六张图，会漏掉重要内容。

第3篇是西岛亲子体验：晴天观海、挖沙、环岛交通、碎石穿鞋与退潮赶海提醒。作者说明部分网红点未亲自拍摄，不能把它们升级成作者明确亲历的路线。第4篇明确推荐西岛，给出一条约两小时的沿海走拍路线。第5篇是后海正向亲历，虽然提及很多网上差评，但不能将转述计成多篇负面证据；临海住宿噪声和冲浪选择是条件提醒，三和风味馆与丹姐清补凉是具体餐饮推荐。

## 完整行程样例：三亚五天四晚

以下只用于体验样例。五天四晚取自第1篇，不是用户已确认的旅行长度；示例假设Day1上午抵达、Day5傍晚或晚间返程，普通休闲节奏，以海边散步、拍照与餐饮为主，无已购或锁定项目。日内顺序和住宿区域是AI编排建议，不是原作者统一给出的行程。生产应使用实际行程的日期和约束，不套用这些假设。本样例不用虚构酒店、票价或精确交通分钟数。

样例复核更正：初版把后海放在Day5，是先按素材顺序填天、再局部加返程兜底，没有先给“返程日”设置全局角色，属于编排缺陷，不是因为前四天已经排满。凤凰机场在三亚西侧，后海位于东侧且存在拥堵、活动超时等不确定性，通常不应成为返程日默认安排。无已订酒店约束时，更合理的总体方向是先处理市区与东侧，再逐步向机场所在的西侧收束。

### Day1：大东海慢逛 → 鹿回头（抵达日）

上午抵达、安顿后在大东海慢慢逛、吃饭。傍晚按精力决定是否去鹿回头看城市与海湾景色；抵达晚或疲劳时直接取消，不压缩接驳和休息。小东海赶海保留为其他完整游玩日的备选，须按当天潮汐与现场安全判断。

今晚住处优先沿用用户已订酒店。没有住宿约束时，区域建议必须与后续东侧行程和整体换宿成本一起计算，不能只因当天景点临时推荐一家酒店。

### Day2：后海村逛吃与冲浪氛围（远端完整游玩日）

把后海放在中前段的完整游玩日，而不是返程日。这里适合逛吃、看冲浪和体验渔村氛围。三和风味馆可以成为餐饮建议，第5篇有连续多次用餐的具体经历，并建议微辣；丹姐清补凉作为同区域补充，不要求专门再跑一趟。

想体验冲浪时，第2篇提醒先比较教练和学员评价，不着急付款；不默认安排付费体验。第5篇说临海民宿夜间有噪声，应影响喜静用户的住宿选择，而不是把整个后海判为避雷。若从已订酒店往返后海明显不顺路，AI应说明代价并提供“保留后海 / 改为近处慢游”的选择，而不是偷偷调整酒店。

### Day3：亚龙湾一带，公路风景与海滩

以亚龙湾海滩为主。喜欢雨林、且体力与交通允许，可以加亚龙湾森林公园，按第2篇提示准备防晒和驱蚊；不是每个用户都必须加。自驾时太阳湾公路作为顺路风景备选，不为非自驾用户强插一次往返。不要在路边停车拍照；第2篇所称观景台停留规则需核对。

第2篇建议下午四点后到亚龙湾海滩，作为减少暴晒的安排参考，不代表精确日落时间或保证天气。入口的小通道只是攻略线索，不能当成现时必定开放的通行保证。当天不同时叠加森林公园、公路、蜈支洲和夜市，避免把素材中所有推荐都塞进去。

### Day4：西岛，沿海走拍与闲逛（向机场方向收束）

西岛保留大半天，不强塞另一个海岛。四篇有西岛相关信息，但不能显示成“四篇强推”。第3、4篇有具体体验，第1篇是路线与提示，第2篇是两岛比较。

内部玩法沿第4篇的路线展开：码头出入口左转的彩色西岛字母 → 西岛墙 → 木门与歪脖子椰子树 → 珊瑚墙前的椰林沙滩 → 小吃街 → 珊瑚墙 → 临海公路 → 孤独的树。作者这段走走拍拍约两小时；这不是全岛总耗时，也不包含完整往返、排队、吃饭和深度环岛。

木门与歪脖子椰子树原文提到排队，赶时间可以跳过，把椰林沙滩作为拍照替代。亲子用户应保留穿鞋提醒：沙滩碎石、贝壳与珊瑚不适合光脚跑。第3篇提供三轮车、电动车和观光车的体验参考，价格与运营需要另核对。牛王岭日落、海上书屋作为备选玩法，不并入“两小时路线”。

晴天观海是第2、3篇共同提到的条件；实际天气差时提出与陆地日互换的建议，不静默移动已锁定安排。最后一晚若住宿未定，可建议回到三亚湾或机场方向；住宿已订则按真实锚点重算，不为优化路线擅自换酒店。

### Day5：机场方向的低承诺安排 → 返程

返程日先从航班时间、最后一晚酒店、行李存放与到机场缓冲倒推“最晚离开游玩点的时间”。早班机只安排退房和接驳；较晚航班才从三亚湾散步、天涯小镇短停等低承诺选项中选一个。是否能去仍取决于真实交通与缓冲，不能因为地理相对接近就保证赶得上。

椰梦长廊看日落只适用于航班足够晚且不影响值机的情况，不能为了使用攻略Tips固定塞入返程日。返程日默认不排海岛、船班、长门票景区、付费水上活动、天气高度敏感或退出时间不可控的项目；用户明确要求时，展示风险和取舍后再排。最后一天不再放“今晚住”。

### 候选与取舍

蜈支洲岛不是被避雷，而是本版把海岛体验重点留给资料更丰富的西岛。第2篇明确提出时间紧时两岛可二选一；偏好水上项目、已购票或指定蜈支洲时，优先采用用户约束，重新组织同区域安排。不能在有已购票时仍擅自用西岛替换。

南山、天涯海角、免税城、亚特兰蒂斯与各餐厅保留为有来源的候选或补充，不把所有名字变成必去。用户说“想去南山”时应替换适当时段，而非无脑继续叠加。地图底图上的酒店标签、喜来登对照酒店和无关广告不自动变成推荐。

## 点亮点后怎么看原文

推荐两层而不是二选一。点击某条亮点或Tips，先打开对应来源的原句及必要上下文；一句归纳涉及多篇时，显示各篇对应片段。片段再提供“展开这篇”和“打开原链接”。用户先验证这个判断，需要作者上下文时再看整篇，不每次都被送到一篇长攻略的开头。

例如点“走拍约两小时”，先看到第4篇这条路线结尾的原句，并能展开前面的完整路线。点“沙滩穿鞋”，看到第3篇的亲子提醒，而不是第4篇的拍照心得。第2篇的图片信息显示当时的对应原图，定位到区域；没有准确框选坐标时定位到整张图，不伪造高亮。OCR文字应标为识别文字，不冒充原作者的数字原文。

“展开这篇”展示导入时保存的正文和已保存图片，注明来源、作者、导入时间与覆盖情况。它是导入时快照，不是实时小红书网页；不复制整站页面，不承诺保存评论、视频或所有动态内容。原站入口保留，方便用户看当前版本、评论与作者信息。

## 保存原文的技术边界

核心存储没有明显技术障碍。现有SourceEvidence与sourceMentionRefs已经能关联景点和原句，需要把不同亮点精确绑定到各自片段；整篇内容按一个来源文档保存，片段只引用它，不给每个景点复制全文。

保存已提交文字、截图、取回的正文、标题、作者、时间及原链接；图片要保存已获准取回的实际文件，而不仅是可能过期的远程地址。原图留存与OCR数量分开：可以保存图，但不必对摄影图全做识字。存储按行程隔离，不能把用户的攻略快照塞进公开仓库或评委共享素材区。共享访问码不是多用户数据隔离，服务器端还需校验所属行程的访问权限；匿名演示至少用独立、不可猜测的行程会话并验证归属。

难点主要在取回和定位，而不是保存。链接可能登录受限、失效、被删；本次已登录Chrome读取成功不能保证云服务器出口成功，也不能把用户登录状态带去共享服务器。图片地址可过期，图中文字可能识别错，原文后来可修改。完整快照必须按实际覆盖情况命名；只有正文和部分图时不能声称“整篇已完整保存”。平台条款和版权还需遵守：仅按用户发起供本人参考，默认不公开全文；不承诺商业化复制小红书内容合法。

## 哪些细节需要产品规则，哪些让AI判断

产品必须规定权限与结果边界：不得擅自改已定天数、预算上限、航班、已购与锁定内容；不得将未知交通当零；不得把总结标成原文；不把条件性玩法风险升级成整点劝退；证据不可跨行程泄漏。这些需进入程序校验，不只靠提示词。用户已定义的明确“不去X”优先于攻略多数推荐。

AI可以判断同名归并、内容重复、攻略与用户偏好的关联、何时适合放哪个玩法、同区域餐饮怎么顺路补入，以及哪些意见可用条件解释。不做复杂来源分数，不将两篇提到当成两篇强推。编排和新估算允许存在，但必须与攻略原句分开，不能伪装来源。新地点若来自模型常识而非用户素材，沿用FlyAI验证与现有创建护栏，不凭空造正式点位。

AI也可以发现信息缺口，但不能仅因几篇攻略重复，就判断必须缩短旅行。一个海岛加酒店休息能覆盖一天，喜欢慢游的人并不需要每天增加很多点。先按用户节奏判断：是否能合理覆盖每天，是否存在被迫空白或为填满而过度重复。

真的不足时只问会改变结果的关键决策。日期灵活时，可问“这批攻略集中在西岛，按你的节奏适合约三天；要先排三天，还是保留五天并补其他区域？”这里的三天是AI建议，不是确定事实。已定五天时，不把缩成三天当默认选项，改问“保留五天，以慢游休息为主，还是允许补充攻略外景点？”已授权AI补充则不再重复问；新增来源与验证要求仍须满足。没有授权时先给可行的已有部分并保留缺口，不编出一份看似完整的行程。

多篇攻略里某点的强推不能自动变成用户必须去；素材有价值不等于认可全文。不必为每一个咖啡馆、每条Tips征求确认。澄清应集中为一次关键选择，用户答完直接出完整草案，不进入连环问答。

## 本次慢在哪里，产品如何改

本轮耗时混入了浏览器工具多轮往返、泛用取文抓到评论后的校正、九张文字图人工识读、产品推敲、核查与会话等待。它不是GoPlay五篇攻略的一次端到端运行；不能据此断言生产需要半小时，也不能承诺生产一定一分钟。工具记录中，五个页面导航各约0.9至1.8秒，但这仅是导航，不是全量提取、识图与排程时间。

产品实现应定点读取目标noteId，不对整页做泛用摘要；同noteId去重缓存，文字与原图一次取回后复用；从内容类型选择识字图，摄影图不重复OCR；图片视觉识读分组处理，按供应商限额控制并发；多篇抽取结果合并后做一次全行程编排，不重复执行“每篇总结→每篇排程→合并再排”。外站抓取仍需限流，不能为快而无限并发。

用户第一次看到的应是可读的完整草案。正文与关键文字图处理完后先出基础版，其他可选细节完成时只补充亮点和Tips；不能自动改已展示的行程结构、日期或已接受内容。关键文字图未读到则如实告知素材处理范围，不用“已整理五篇全部内容”掩盖遗漏。耗时可选任务不阻塞已有结果，整篇回看需要时再加载较大的原图。

建议小Q测缓存命中、首次五篇纯文字、首次五篇含图、单条受限链接四种情况，逐段记录取回、图像、合并和排程耗时与P50/P95。初步体验目标是30秒内有实质结果、通常60至90秒形成可微调草案；这是待验证的设计目标，不是现有性能。超时到约90秒应停止无提示等待，返回已完成的可用草案与遗漏范围；剩余可重试，不能伪造成功。若固定测试集达不到，优先改管线和识图预算，再重新承诺等待时间。

## 本次验收重点

五篇重复不会只剩几串点名；西岛的内部路线、两小时适用范围和穿鞋提示都能留住。后海的转述差评不会计成多篇劝退，冲浪教练风险不会整村屏蔽。单篇餐饮体验能进入顺路补充，无关广告与比较酒店不成为推荐。点任一亮点能定位到正确笔记原句或原图；来源数按笔记去重。日期已定时不擅自缩短，不足才进行必要的一次澄清。生成结果没有未知占零、来源伪装和静默覆盖。
